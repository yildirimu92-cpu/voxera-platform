# Voxera Launch-Readiness Deep Audit (2026-04-06)

## Scope and method
This audit reviews the current repository implementation of:
- Admin portal (`admin-panel/index.html`, `admin-panel/index-v2.html`)
- Customer dashboard (`customer-dashboard/index.html`)
- Netlify backend functions (`admin-panel/netlify/functions/*.js`)
- Supabase SQL migrations (`supabase/sql/*.sql`)

Method used: static architecture and product-flow analysis with launch-readiness framing (product, UX, operations, data, scalability, and GTM fit).

---

## A. Executive Summary (brutally honest)
Voxera is **not launch-ready for a serious SaaS go-live** in its current state.

You have an impressive amount of UI surface area and many “looks-complete” modules. But structurally, the system still behaves like a hybrid MVP/prototype:
- critical backend operations are callable without visible auth verification in functions,
- contracts and important workflow states are partly local/placeholder,
- admin v2 is seeded with static in-memory data,
- lifecycle and numbering logic is inconsistent or absent,
- billing is partly simulation + manual mailto flows rather than auditable finance workflows,
- there is no strong end-to-end audit trail model for operations.

Conclusion: **technically demoable, commercially risky**.

---

## Detailed Issues

### 1) Publicly callable privileged Netlify functions
- **Where:** `admin-panel/netlify/functions/create-customer.js`, `activate-subscription.js`, `delete-customer.js`, `send-welcome.js`
- **Problem:** Functions rely on service-role credentials but expose permissive CORS (`*`) and do not validate an admin JWT/session/role before destructive or privileged actions.
- **Severity:** **critical**
- **Recommended fix:** Introduce signed server-side auth verification (Supabase JWT + role check in `admins` table), deny unauthenticated requests, restrict CORS origins.
- **Launch blocker:** **Yes**
- **Type:** technical / operational / strategic

### 2) Admin v2 is mostly a simulated operations center
- **Where:** `admin-panel/index-v2.html`
- **Problem:** Core entities are hardcoded in a `state` object; workflows mutate in-memory objects instead of durable backend records. This creates false confidence and no persistence.
- **Severity:** **high**
- **Recommended fix:** Either deprecate v2 until fully wired to backend, or complete migration with real queries/mutations and remove static seed dependency.
- **Launch blocker:** **Yes**
- **Type:** product / operational / strategic

### 3) Duplicate state blocks in admin v2 indicate governance drift
- **Where:** `admin-panel/index-v2.html`
- **Problem:** `admins`, `featureFlags`, `aiGlobal`, `aiConfigs`, `aiChanges` are duplicated in the same state object, increasing defect risk and ambiguity.
- **Severity:** **high**
- **Recommended fix:** Normalize state declarations; enforce linting/tests for duplicate object keys and unreachable config.
- **Launch blocker:** No (but very risky)
- **Type:** technical

### 4) Contract handling is not production-grade (localStorage persistence)
- **Where:** `admin-panel/index.html`
- **Problem:** Contracts are explicitly stored in browser localStorage and rendered as if operational records. This is not multi-user, not auditable, and not legally robust.
- **Severity:** **critical**
- **Recommended fix:** Store contracts and versions in DB + object storage with immutable file audit trail, actor log, and retention policy.
- **Launch blocker:** **Yes**
- **Type:** product / operational / legal / strategic

### 5) Billing actions are commercially weak and non-systemic
- **Where:** `customer-dashboard/index.html`
- **Problem:** Upgrade/add-on requests rely on `mailto:` flows; no structured order pipeline, approval state, invoice linkage, or billing event model.
- **Severity:** **high**
- **Recommended fix:** Build billing request objects + approval flow + subscription amendments + invoice generation + webhook confirmations.
- **Launch blocker:** **Yes** for scalable launch
- **Type:** product / operational / strategic

### 6) Missing invoice and credit-note system
- **Where:** repository-wide (no invoice/credit-note schema or workflows)
- **Problem:** There is no explicit invoice entity lifecycle (draft/issued/paid/overdue/void) or credit-note process.
- **Severity:** **critical**
- **Recommended fix:** Introduce financial core tables and numbering + reconciliation states + export/accounting integration.
- **Launch blocker:** **Yes**
- **Type:** product / operational / strategic

### 7) Numbering systems are incomplete and inconsistent
- **Where:** mixed `customers.id`, UI-generated case IDs (`C-###`), no invoice/credit numbering
- **Problem:** Customer IDs are generated by reading max +1 from text ids; cases use ad-hoc prefixes; contracts and invoices lack formal numbering strategy.
- **Severity:** **high**
- **Recommended fix:** Centralized number allocator per entity type with uniqueness constraints and sequence tables.
- **Launch blocker:** **Yes** (for finance/support quality)
- **Type:** product / data / operational

### 8) Status models are fragmented and weakly governed
- **Where:** admin + dashboard + SQL + UI labels
- **Problem:** Status vocabularies vary (`active/pending`, `Aktiv/Onboarding/Paused`, case statuses, call statuses, readiness labels). This complicates automations and reporting.
- **Severity:** **high**
- **Recommended fix:** Canonical lifecycle enums with transition rules and guards.
- **Launch blocker:** **Yes**
- **Type:** product / data / operational

### 9) Activation flow has brittle assumptions
- **Where:** `activate-subscription.js` and customer status model
- **Problem:** Activation only allowed from `pending`; reactivation and historical subscriptions are acknowledged as future work but unresolved for real lifecycle complexity.
- **Severity:** **medium-high**
- **Recommended fix:** Introduce subscription versioning (`active`, `paused`, `canceled`, `ended`) and contract-bound lifecycle transitions.
- **Launch blocker:** No (for pilot), Yes (for scale)
- **Type:** product / data

### 10) Admin permission enforcement is too UI-centric
- **Where:** `admin-panel/index.html`
- **Problem:** Role guards hide components but privileged API actions are not consistently enforced server-side in corresponding functions.
- **Severity:** **critical**
- **Recommended fix:** Capability matrix enforced in backend endpoints and DB policies; UI should only reflect permissions, not enforce them.
- **Launch blocker:** **Yes**
- **Type:** technical / operational / security

### 11) Auditability is insufficient for enterprise trust
- **Where:** across flows (customer create/delete/activate/case actions)
- **Problem:** No clear immutable event log with actor, before/after payload, reason, source channel, correlation ID.
- **Severity:** **high**
- **Recommended fix:** Event-sourced audit table and mandatory write middleware for critical mutations.
- **Launch blocker:** **Yes** (for serious B2B rollout)
- **Type:** operational / strategic

### 12) Onboarding persistence has local-device behavior in customer UI
- **Where:** `customer-dashboard/index.html`
- **Problem:** Setup progress uses localStorage flags, which risks mismatch across devices/users and weak operational visibility.
- **Severity:** **high**
- **Recommended fix:** Persist onboarding step state server-side with timestamps, actor, and required evidence markers.
- **Launch blocker:** No (small pilot), Yes (100+ customers)
- **Type:** UX / operational / data

### 13) Cases/ticketing model is underdeveloped
- **Where:** admin v2 cases and dashboard call handling
- **Problem:** Cases are simplistic, lacking SLA clocks, assignee workflow, escalation paths, tags, linked entities (call/contract/invoice), and robust status transitions.
- **Severity:** **high**
- **Recommended fix:** Formal ticket domain model with queueing, SLA, assignment history, and resolution taxonomy.
- **Launch blocker:** **Yes** for operations-heavy launch
- **Type:** product / operational

### 14) Notification logic is ambiguous and partially legacy
- **Where:** customer notification mode fallback logic
- **Problem:** New `notification_mode` coexists with legacy booleans and fallback inference; risk of incorrect notification behavior.
- **Severity:** **medium-high**
- **Recommended fix:** Migrate to single source field (`notification_mode`) with one-time migration and deprecation of legacy flags.
- **Launch blocker:** No (but quality risk)
- **Type:** product / data

### 15) Customer/admin workflow asymmetry can create support conflicts
- **Where:** dashboard vs admin behavior
- **Problem:** Customer sees “systemic” statuses and usage, while admin has partially synthetic and partially real models. Operational decisions can diverge from customer reality.
- **Severity:** **high**
- **Recommended fix:** Shared canonical domain services and one status dictionary used by both interfaces.
- **Launch blocker:** **Yes**
- **Type:** product / strategic

### 16) Scalability risks in list rendering/query patterns
- **Where:** dashboard/admin call and customer table patterns
- **Problem:** Broad fetch + client filtering patterns and limited pagination strategy will degrade at 100–200+ customers with heavy call volume.
- **Severity:** **high**
- **Recommended fix:** Server-side pagination, indexed filters, cursor-based APIs, and lazy loading of heavy sections.
- **Launch blocker:** No for tiny pilot; Yes for target scale
- **Type:** technical / strategic

### 17) “Present but conceptually weak” AI setup
- **Where:** admin v2 AI setup panels
- **Problem:** AI configuration UX exists but lacks robust publishing/version rollback/audit/change approvals by plan tier.
- **Severity:** **medium**
- **Recommended fix:** Add config versioning, publish workflow, impact preview, per-customer overrides with inheritance.
- **Launch blocker:** No
- **Type:** product / operational

### 18) Mobile responsiveness likely acceptable for dashboard but weak for admin operations depth
- **Where:** admin layouts are desktop-heavy tables and dense toolbars
- **Problem:** Mobile ops use-cases (on-call intervention, urgent callback triage) are not clearly first-class in admin.
- **Severity:** **medium**
- **Recommended fix:** Mobile triage mode with priority queue, one-tap callbacks, and compact incident cards.
- **Launch blocker:** No
- **Type:** UX / operational

### 19) Repository hygiene indicates architecture indecision
- **Where:** root-level `activate-subscription.js` and `delete-customer.js` stubs, historical docs
- **Problem:** Stray pseudo-code files near production code increase confusion and maintenance risk.
- **Severity:** **low-medium**
- **Recommended fix:** Remove/archive non-runtime stubs and enforce source-of-truth directories.
- **Launch blocker:** No
- **Type:** technical / operational

### 20) Starter/Business/Pro differentiation is pricing-centric, not capability-centric
- **Where:** plans in dashboard/admin
- **Problem:** Plan differentiation focuses mostly on minutes and price, with insufficient feature-gating and operational entitlement controls.
- **Severity:** **high**
- **Recommended fix:** Define entitlement matrix (AI features, SLA, seats, integrations, reporting depth, support channel, callback automation).
- **Launch blocker:** **Yes** for GTM clarity
- **Type:** product / strategic

## D. Recommended Target Architecture for V1 launch
1. **Single source of truth:** Supabase/Postgres for all transactional entities.
2. **Backend-for-frontend layer:** Netlify/Supabase functions with strict auth and capability checks.
3. **Domain modules:**
   - Customer/Account
   - Telephony events/calls
   - Cases/tickets
   - Onboarding
   - Contracts
   - Billing (subscriptions/invoices/credit notes)
   - Notifications
4. **Event + audit layer:** append-only event store + denormalized read models.
5. **Asynchronous processing:** queues for webhook ingest, notifications, retries, dead-letter handling.
6. **Observability:** central logs + metrics + alerts + admin incident console.
7. **Plan entitlements:** centralized policy object consumed by UI + backend.

## G. Suggested status model

### Customers
- `lead` → `trial` → `onboarding` → `active` → `at_risk` → `suspended` → `churned`

### Onboarding
- `not_started` → `in_progress` → `blocked` → `ready_for_go_live` → `live` → `failed`

### Cases
- `new` → `triaged` → `in_progress` → `waiting_customer` / `waiting_internal` → `resolved` → `closed`

### Contracts
- `draft` → `sent` → `viewed` → `signed` → `active` → `amended` / `terminated` / `expired`

### Invoices
- `draft` → `issued` → `sent` → `partially_paid` / `paid` / `overdue` / `void`

### Calls
- `ingested` → `classified` → `requires_callback` / `no_action` → `callback_scheduled` → `callback_done` → `closed`

## H. Suggested numbering systems
Use immutable, monotonic sequences with yearly partition where useful.

1. **Customers:** `CUS-YYYY-000001`
2. **Cases:** `CAS-YYYY-000001`
3. **Contracts:** `CTR-YYYY-000001` (+ amendment suffix `-A01`)
4. **Invoices:** `INV-YYYY-000001`
5. **Credit notes:** `CRN-YYYY-000001`

Rules:
- Never reuse numbers.
- Sequence issuance only server-side in transaction.
- Store both `display_number` and `sequence_int`.
- Keep legal docs immutable once issued.
